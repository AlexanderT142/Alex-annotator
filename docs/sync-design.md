# 多设备同步（附加模块）设计说明

> 状态：第一期已实现，自动化测试通过；尚未在两个真实 vault 之间手动验证。分支：`feat/sync-addon`
> 背景：GitHub issue #9，用户反映批注无法通过 Obsidian Sync 同步。讨论过程见 `docs/sync-brief.md`。

## 实现记录：与下文设计的差异

下文是动工前的设计。实现时做了这些调整，以代码为准：

1. **每台设备每个 PDF 只有一个分片文件**：`_pdf-annotator-sync/<sha256>/<deviceId>.md`，标注集元数据和批注放在同一个文件里，而不是按集拆成多个文件。这样文件更少，"一部分到了、一部分没到"的情况也更少。
2. **不使用"先写临时文件再改名"**：不同 adapter 对"改名覆盖已有文件"的行为不可靠。改为依赖首尾标记、重试，以及缓存上一次完整读到的版本。
3. **旧数据导出的版本号使用非加密的 64 位哈希**（同步计算），不用 SHA-256，因为这里只需要确定性。
4. **baseline 记录了"用户当时看到的版本"**（`clocks`：各版本的版本向量和时间戳）。实现时发现：如果本地修改要等到下一次同步周期才被检测到，而这期间刚好到达了远端的并发修改，按原设计这次本地修改会被错误地当成"已经看过远端版本"，远端的文字就会被悄悄吞掉。现在本地修改只会取代 baseline 里记录的那些版本。模拟测试能抓到这个 bug：故意改回原来的写法后，第 34 号种子就会丢失笔记。
5. **本机数据目录按设备区分**：`.pdf-annotator/sync/<deviceId>/<sha256>/`，里面有 `baseline.json`、`own.json` 和 `snapshots/`。这样即使用户用 iCloud 之类的工具同步了隐藏文件夹，不同设备的状态也不会混在一起。`own.json` 是本设备已发布分片的本地副本；如果磁盘上的分片和本机记录的 writeNonce 对不上，就判定为设备 ID 被复制。
6. **大量删除拦截的阈值**：超过 5 条，或者至少 3 条且超过总数的 20%。
7. **编辑时暂缓应用按整篇 PDF 处理**：只要焦点在插件界面（类名带 `lpa-`）内的 textarea、input 或 contenteditable 上，就暂缓应用远端修改。这样不需要改卡片编辑器。
8. **核心改动比预算更小**：`annotation-sets.ts` 只新增了两个方法，`syncSnapshot()` 和 `applySyncedChanges()`，取代原计划的 `ensureSet` 和 `setArchived`；两个视图各加了 3 行左右；`main.ts` 加了设置项、启停逻辑和 4 个命令。
9. **开启同步后，已经打开的 PDF 需要重新打开**才会开始同步。修改同步文件夹要等下次启动同步时才生效。

10. **第二轮安全加固（原则：安全网本身也是没测过的代码，必须足够简单）**：
    - **开启前备份**：同步第一次处理某个 PDF 之前，保存一份完整快照（`pre-sync-backup.json`，包括所有集，已归档的也在内），永不轮换。用命令"恢复到开启同步之前"还原，还原逻辑和撤销共用同一套。
    - **快照**：只在远端修改即将写入本地之前拍，本地编辑不拍；每个 PDF 最多保留 15 份滚动。
    - **先校验再应用**：`applySyncedChanges` 先校验整个修改计划，任何一项不合格就整体拒绝；如果中途仍然出错，引擎用应用前的快照把内存状态还原。不替换内存对象，以免影响视图持有的引用。
    - **熔断**：单个周期主线程耗时超过 300ms，就把间隔加倍（最多 60 秒）；到了 60 秒仍然慢，就暂停。10 分钟内出现超过 10 次"没有用户或 AI 改动却写了分片"，判定为循环并暂停。同步自身引起的改动在 `isApplying` 标志内同步触发，有测试验证。
    - **渲染防护**：两个视图的每条批注都在 `renderGuard` 里绘制，一条出错就跳过这一条。同步层只做基本结构校验，不再限制 `type` 等枚举值，以保证向前兼容。
    - **隐藏同步文件夹**：开启同步时用 CSS 在文件列表里隐藏；设置里提供一个按钮，把文件夹加入"排除文件"，重复点击不会重复添加，并且总是绑定当前配置的文件夹。
    - **不做**：拖动或缩放便签时暂缓应用远端修改，因为需要加锁状态，有卡死的风险。保留现有的"焦点检查"，它不需要任何锁状态。

11. **暂停反馈与恢复**：每个 PDF 都记录暂停原因（出错、卡顿、循环、撤销、恢复）。在暂停状态下运行"立即同步"，会说明暂停原因，而不是提示"synced"。"恢复同步"也能解除出错导致的暂停：清零失败计数，并换一个全新的引擎，从磁盘重新加载状态，不需要重启 Obsidian。撤销和"恢复到开启同步之前"绕过熔断，因此在同步出错时也能用。原生视图的侧边卡片，创建和刷新都放进了 `renderGuard`，创建失败时会删除只建了一半的卡片。
12. **有意不做**：修改同步文件夹后即时生效（仍需切换开关或重启）；退出 Obsidian 时强制执行最后一次同步（在关闭过程中执行异步写入，可能写出不完整的文件。现在的做法是等下次打开该 PDF 时再发布，更安全）。

尚未完成：第 8 节第 6 步，即用两个 vault 搭配 Syncthing 或 Obsidian Sync 手动试一遍。

## 0. 最高原则：同步是附加模块，不是核心改造

**同步功能哪怕完全失效、充满 bug，插件也至少要和现在的版本一样好用。**

具体约束：

1. **默认关闭。** 关闭时同步代码一行都不执行：不注册监听，不读写同步文件夹。行为与 0.4.0 完全一致。
2. **核心存储不变。** `.pdf-annotator/bundles/sha256/<hash>/` 仍然是唯一真实数据源，格式、路径、备份机制一律不改。同步模块只是一个"复制器"：把本地数据导出到同步文件夹，再把别的设备的修改导入本地。
3. **同步模块不直接写核心文件。** 所有导入都通过 `AnnotationSetWorkspace` 的公开方法完成，因此核心已有的 `.previous` 备份、串行保存等保护照常生效。
4. **出错即熔断。** 同步模块的任何异常都在模块边界被捕获。异常发生后，该 PDF 本次会话的同步自动停用，并提示一次 Notice，核心功能继续正常工作。
5. **可以撤销。** 每次把远端修改应用到本地之前，先给该 PDF 的本地数据拍一个快照，并提供"撤销上一次同步"命令。
6. **关闭或卸载不丢数据。** 关闭同步时，本地数据和同步文件夹都原样保留，再打开时从原处继续。

需要坦白的一点：同步模块会把远端修改写进本地。如果合并逻辑有 bug，算出了一个"格式合法但内容不对"的结果，本地数据是会被改的。第 6 节的护栏能让这种情况**可发现、可恢复**，但不能保证它**不发生**。这一点要在设置页的说明里写清楚，并把同步标注为 Beta。

## 1. 范围

### 第一期要做

- 桌面端之间同步批注和标注集元数据（名称、颜色、类型、归档状态）
- 兼容 Obsidian Sync、iCloud、Syncthing、Git、Dropbox 等只认文件的同步工具
- 不会互相覆盖，不会静默丢失笔记文字，多台设备最终状态一致
- 开启时自动把现有批注导出为初始数据，用户无需手动操作
- 第 6 节的全部安全护栏
- 收敛测试

### 第一期不做

- 移动端（插件仍是 `isDesktopOnly`）
- 删除标注集、在集之间移动批注（核心本来就没有这两个功能；第一期规定 `setId` 创建后不可改，集只能归档）
- 同步 PDF 备份（`document.pdf`）、AI 任务进度、视图状态
- 用 CSS 在文件列表里隐藏同步文件夹、一键加入排除列表（第二期）
- 压缩、清理旧数据（大概率永远不需要）

## 3. 数据存放

### 3.1 参与同步的数据

```text
<Vault>/_pdf-annotator-sync/            # 路径可在设置中修改；不能以点开头
  <sha256>/
    sets--<deviceId>.md                 # 本设备写的标注集元数据
    set-<setId>--<deviceId>.md          # 本设备在某个集里创建、修改或删除过的批注
```

- 用 `.md` 后缀，因为 Obsidian Sync 默认同步 Markdown，而其他文件类型默认不同步。
- 一个文件永远只有一台设备写，因此同步工具不会产生冲突。
- 读取时**不靠文件名判断身份**。文件名只用来发现文件，设备和集的身份以文件内 JSON 中的 `deviceId`、`setId` 为准。目录里所有 `.md` 都要读，包括同步工具生成的冲突副本（如 `... (conflicted copy).md`、`*.sync-conflict-*.md`）。这些副本只读，永远不写。

### 3.2 只存在本机的数据

| 数据 | 位置 |
| --- | --- |
| `deviceId` | `app.saveLocalStorage("pdf-annotator:sync-device-id")`。**绝不能**放进 `data.json` |
| 每个分片最后一次写入的 `writeNonce` | `app.saveLocalStorage("pdf-annotator:sync-nonces")` |
| baseline（上次同步时的状态，用来检测本地修改） | `.pdf-annotator/sync/<sha256>/baseline.json` |
| 撤销快照 | `.pdf-annotator/sync/<sha256>/snapshots/<时间戳>/`，每个 PDF 保留最近 10 份 |
| 视图状态（显示哪些集、当前写入哪个集） | 保持核心现状，存在核心的 `index.json` 里。同步模块不导出、不导入这两项 |

## 4. 分片文件格式

````markdown
---
pdf-annotator-sync: 1
kind: set-shard
---

# PDF Annotator 同步数据（自动生成，请勿编辑）

- P.12 “分布式系统中的部分失效是不可避免的。” — 这里和第 4 章呼应

<!-- pdf-annotator-sync:start -->
```json
{ "schema": 1, "kind": "set-shard", "docHash": "...", "setId": "default",
  "deviceId": "dev_k8x9m2", "writeNonce": "r4nd0m", "records": [ ... ] }
```
<!-- pdf-annotator-sync:end -->
````

- 只有同时找到 start 和 end 两个标记，并且中间的 JSON 能解析成功，才算完整文件。否则按 300ms、800ms、2000ms 的间隔重试，仍然失败就跳过该文件并记录警告。**跳过的文件绝不能被当成"空数据"参与合并。**
- frontmatter 和摘要只给人看，程序不读，所以被 Linter 之类的插件改动也不影响。
- 写入时使用"先写临时文件再改名"的方式，减少同步到半截文件的概率。

## 5. 数据模型与算法

### 5.1 同步记录

```ts
type DeviceId = string;
type VV = Record<string, number>;            // 版本向量，如 { dev_a: 2, dev_b: 1 }

interface SyncHighlightRecord {
  id: string;
  setId: string;                              // 不可变
  created: string;

  // 删除状态（LWW）
  deleted: boolean;
  statusTs: number; statusBy: DeviceId;

  // 样式与结构（LWW，整体比较）：Highlight 中除 id/setId/created/note/noteContentCJK 以外的全部字段
  meta: Omit<Highlight, "id" | "setId" | "created" | "note" | "noteContentCJK">;
  metaTs: number; metaBy: DeviceId;

  // 笔记正文（版本向量）
  note: string; noteContentCJK: string;
  noteVV: VV;
  noteTs: number; noteBy: DeviceId;           // 只用于排序和显示，不用于判断因果
}

interface SyncSetRecord {
  id: string; name: string; kind: AnnotationSetKind; accent: string;
  created: string; archived: boolean;
  ts: number; by: DeviceId;
}
```

`meta` 直接复用核心的 `Highlight` 字段，同步模块不在核心类型上加任何字段。

### 5.2 本设备只写自己动过的记录

设备 A 的分片里只放 A 创建、修改或删除过的批注。如果 A 只改了 B 创建的某条批注的颜色，A 要把这条批注的整条记录写进自己的分片，其中笔记部分（`note`、`noteVV`、`noteTs`、`noteBy`）从合并结果**原样照抄**，不能生成新版本。

### 5.3 时间戳规则

修改某条记录的某个部分时：

```ts
ts = Math.max(Date.now(), 该记录该部分当前的 ts + 1)
```

时间戳只按记录比较，不做全文档的最大值传递。即使某台设备时钟错到 2030 年，也只会影响它改过的那几条记录，而且之后的正常修改仍然能覆盖它们。

LWW 比较规则：`ts` 大的赢；`ts` 相同时比较 `deviceId` 的字典序。

### 5.4 笔记版本向量

- **保存新笔记：** 新的 `noteVV` = 合并结果中该批注所有当前版本（heads）的 VV 逐项取最大值，再把本设备那一项加 1。
- **合并：** 不被任何其他版本严格支配的，就是当前版本（head）。
  - VV 相同、内容也相同：视为同一个版本，去重。
  - VV 相同、内容不同：视为冲突。这种情况只会出现在设备 ID 被复制的时候。
  - 去重后只剩一个版本：就用它。
  - 剩多个版本：按 `noteTs` 从新到旧排列，以最新的为正文，其余附在后面：

    ```text
    （最新版本）

    ---
    [同步冲突保留 · <deviceId> · <UTC 时间>]
    （其他版本）
    ```

    拼接结果必须是确定性的，所有设备算出来要一字不差。
- **冲突的消解：** 用户编辑并保存这条笔记后，新 VV 支配所有旧版本，冲突自然消失。

### 5.5 删除与恢复

- 删除时不移除记录，只设 `deleted: true` 并更新 `statusTs`。
- 生效规则：`deleted && statusTs >= noteTs` 才算已删除。也就是说，删除之后另一台设备如果写了新笔记，这条批注会保留下来。

### 5.6 标注集

- 标注集元数据按 LWW 合并。
- 如果某个集的批注分片先到了，但集的元数据还没到，就先生成一个临时集（名称为"同步中的标注集 (<id 前 6 位>)"），等元数据到达后再更新名称和颜色。
- 两台设备各自新建同名的集，会得到两个不同 id 的集。这是预期行为，不做合并。

### 5.7 合并必须是纯函数

`merge(shards[]) -> MergedState` 不读写文件，与输入顺序和重复无关，相同输入一定得到相同输出。

## 6. 运行流程与安全护栏

### 6.1 首次开启

1. 生成 `deviceId`。
2. 对每个已有 bundle：读取本地数据，转换成同步记录。初始版本使用**确定性版本号**：
   - `noteVV = { ["legacy_" + sha256(id|note|noteContentCJK).slice(0, 8)]: 1 }`；笔记为空时 `noteVV = {}`。
   - `metaTs`、`statusTs` 和 `noteTs` 都取 `Date.parse(created)`，`by` 都记为 `"legacy"`。

   这样两台设备各自导出同一份旧数据，结果完全一样，不会产生假冲突。
3. 写出本设备分片，并保存 baseline。
4. 首次开启可以只处理"打开过的 PDF"，等打开时再导出，避免一开启就扫描整个库。

### 6.2 打开 PDF（`attach`）

1. 读取该 PDF 的所有分片并合并。
2. 把合并结果和本地数据比较，算出差异，经过护栏检查后，通过 API 应用到本地。
3. 用本地的最新状态生成本设备分片，必要时写出，并更新 baseline。

### 6.3 本地修改

监听 `workspace.onChange`，防抖 2 秒后：用当前本地状态和 baseline 比较，找出改动的记录（按字段哈希判断改的是 `meta` 还是 `note`；baseline 里有、本地没有的就是删除），按第 5 节规则更新记录，然后写出本设备分片。

### 6.4 远端修改

监听同步文件夹的 `create`、`modify`、`delete`、`rename` 事件：

- 先过滤掉自己写入引起的事件（对比写入后记录的内容哈希）。
- 按 PDF 防抖 400ms 后，如果该 PDF 正在打开，就执行 6.2 的第 1、2 步。
- 如果用户正在编辑某张卡片，暂缓应用，等编辑框失焦后再应用。

**读取不能触发写入。** 应用远端修改之前，先把 baseline 更新为合并结果。这样应用后触发的 `onChange` 比较出来没有差异，也就不会再写分片，避免设备之间来回写。

### 6.5 deviceId 被复制的检测

每次写入分片时生成新的 `writeNonce`，并记在本机。读取到自己名下的分片时，如果其中的 `writeNonce` 和本机记录不一致，说明另一台机器在用同一个 ID（比如整机迁移或从备份恢复）。这时立刻换发新 ID，旧分片保留为只读，并提示一次 Notice。

### 6.6 护栏（核心要求，不能省）

1. **熔断：** `attach`、监听回调、定时任务的入口全部用 try/catch 包住。出现异常时，本会话内停用该 PDF 的同步，提示一次 Notice，并在控制台打印完整错误。同一会话内累计 3 次异常，就停用整个同步模块。
2. **应用前快照：** 每次应用远端修改之前，先把该 PDF 的 `annotation-sets/` 目录复制到 `snapshots/`。命令"撤销上一次同步"会把最近一份快照还原回本地，同时暂停该 PDF 的同步，避免马上又被同步回来。
3. **大量删除拦截：** 一次应用如果要删除超过 5 条批注，或超过该 PDF 批注总数的 20%，就不自动应用，改为弹出确认，说明要删多少条、来自哪台设备。
4. **数据校验：** 从远端来的每条记录都要通过基本校验：`page` 为非负整数，`rects` 是数组且坐标是有限数，`color` 是字符串，`setId` 非空。不合格的记录跳过并记录日志，不影响其他记录。
5. **只增不减：** 同步模块不调用任何删除整个集或整个文件的方法，唯一允许的删除是批注级的 `remove(id)`，并且受第 3 条约束。
6. **关闭即停：** 关闭开关后立刻注销所有监听，不做任何清理性的删除。

## 7. 测试

新代码放在 `src/sync/`，测试放在 `test/sync-*.ts`，复用 `test/memory-adapter.ts` 和 `test/obsidian-stub.ts`。

### 7.1 合并函数单元测试

覆盖第 5 节的每条规则：LWW 和平局处理、时间戳推进、VV 支配和去重、冲突拼接的确定性、删除与笔记修改的先后、临时集、2030 年时钟。

### 7.2 多设备模拟测试（最重要）

模拟三台设备，各自持有内存文件系统：随机执行增、删、改颜色、改笔记、新建集、归档。同步层随机延迟、打乱顺序、重复投递、只投递一部分，偶尔投递半截文件或旧版本文件。所有文件都送达后，检查以下不变量：

1. **最终一致：** 三台设备的合并结果规范化序列化后完全相同。
2. **顺序无关、重复无关：** 对同一组分片，任意排列和重复的合并结果都相同。
3. **不丢笔记：** 任意设备写过的非空笔记，在最终结果中要么是正文，要么被一个支配它的新版本取代，要么完整出现在冲突拼接块里。
4. **读取不写：** 只接收远端修改、没有本地修改的设备，磁盘写入次数为 0。
